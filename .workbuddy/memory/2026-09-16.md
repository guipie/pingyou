## 本地大模型（Ollama）：引擎启动与模型下载解耦 + 卡片级安装进度

### 背景问题
1. `handleInit()` 把「拉起引擎」和「下载模型」揉在一个流程里：装第二个模型时会再次 `start_ollama_engine`，
   而该命令会 kill 掉旧子进程再 spawn 新的 → 端口冲突 + 把正在服务的引擎杀掉。
2. 报错 `未接收到来自本地服务的有效数据流` 是**假象**：`download_model` 里 `if let Ok(status) = res`
   把 Ollama 通过 `{"error": "..."}` 返回的真实失败信息**静默丢弃**了，最后只能落到兜底文案。
3. `ensure_local_provider` 两个 bug：spawn 时漏掉 `OLLAMA_MODELS`（模型目录不一致）；
   `running` 在 spawn **之前**计算，拉起成功后仍返回 `false`。
4. `cleanup_local_models(Some(name))` 先 `stop_ollama_engine()` 再 `delete_model()` → 卸载单个模型必然失败。
5. 进度只有页面级一条进度条，无法按模型区分。

### 落地改动
**Rust `src-tauri/src/ollama/ollama_manager.rs`**
- 状态从 3 个全局 `AtomicBool` 换成按**任务键**索引的 `HashSet`（`active_jobs` / `cancel_flags` / `pause_flags`），
  键 = 模型名，引擎组件用保留键 `__engine__`（`ENGINE_JOB_KEY`）。
- `JobGuard`（RAII）自动登记/摘除任务标志，出错也不卡死状态。
- `DownloadPayload` 增加 `model: String` 字段，前端据此把进度派发到对应卡片。
- `start_ollama_engine` **幂等**：先 `is_engine_running()`，已在跑就直接返回；`engine_start_lock`
  （`tokio::sync::Mutex`）单飞防止自动拉起与手动点击并发；用 `wait_engine_ready` 轮询替代固定 4s sleep；
  `spawn_engine_process` 只在旧子进程已退出时才重新 spawn。
- `download_model` 与引擎解耦：只要求引擎就绪（最多等 20s），已安装则幂等成功，
  **把 stream 的 `Err` 原样透出**，并识别 `status == "success"`。
- `ensure_local_provider` 修复上述 2 个 bug，返回全量模型（去掉 5 条截断）。
- `cleanup_local_models` 拆成两条语义：传 model_name 只 `delete_model`（不动引擎）；不传才停引擎 + 物理删除。
- `pause_download` / `resume_download` / `cancel_download` 都加 `model_name: Option<String>` 参数（空 = 全部）。
- `is_downloading()` 返回值由 `bool` 改为 `Vec<String>`（进行中的任务键）。

**前端**
- 新增 `src/composables/useOllamaEngine.ts`：模块级单例，引擎状态机
  （idle/checking/unsupported/absent/starting/ready/error）+ `installedModels` + `installJobs[modelId]`，
  全局只注册一次 `download-progress` 监听并**按模型名路由**；暴露 `ensureEngine` / `startEngine` /
  `installModel` / `pauseInstall` / `uninstallModel` / `syncProvider` 等。
- 新增 `provider/components/local-model-card.vue`：把进度条、状态文案、暂停/取消/重试都收进**单张模型卡片**。
- 重写 `provider/ollama.vue`：页面级视图只由引擎状态驱动，页面进度条只服务引擎组件下载。
- `App.vue` 启动流程末尾加 `await ollamaEngine.ensureEngine()` → 开机自动拉起引擎并把已下载模型同步为供应商。
- i18n 5 语言补 key：`labels.retry/dismiss`、`status.preparingEngine/resumingInstall`、
  `messages.modelInstalled`、`local.labels.engineError`、`local.hints.engineAbsentDesc`、`local.errors.*`。

## 本地大模型：「提示安装成功但其实没装」的两处根因修复

### 现象
设置页点「安装」后弹出「模型安装成功，已加入本地供应商」，但模型并没有真正装上。

### 根因 1：模型名 `:latest` 前后端不一致（直接原因）
- catalog 里 Moondream 的 id 是 `moondream`（**不带 tag**），而 Ollama `GET /api/tags` 只返回规范名 `moondream:latest`。
- Rust `local_model_exists()` 会补 `:latest` 再比 → 判定「已存在」→ **立刻返回 Ok、毫无下载**；
  前端却用 `installedModelNames.has(id)` **精确匹配** → 永远 false → 卡片一直显示「安装」。
  于是「提示成功 + 卡片没变」的错位。同理 `defaultModel === item.model.id` 也恒不相等，
  用户在 `syncProvider()` 里选的默认模型会被**静默重置**成列表第一个。

### 根因 2：引擎不是「我们的引擎」，模型装到了别的目录
- 磁盘证据：`%APPDATA%/com.guipie.Pingyou/models` 里只有 `qwen2.5:7b`（4.68GB, 9/11），
  而 `~/.ollama/models` 里有 `moondream:latest` + `qwen2.5:0.5b`，且 `qwen2.5:0.5b` 的 blob 是**当天新写入**的。
- 说明 11435 端口上服务着的 Ollama **没有带 `OLLAMA_MODELS`**：旧版 `ensure_local_provider` 拉起的孤儿进程
  （只设了 `OLLAMA_HOST`）一直占着端口，新代码 `if is_engine_running() { return Ok(()) }` 把它当自己的引擎复用了。
- 后果：模型下载到 `~/.ollama`；沙箱里真实存在的 7B 反而显示「未安装」。

### 修复
**Rust `ollama_manager.rs`**
- 新增 `const ENGINE_PORT: u16 = 11435`，替换所有硬编码。
- 新增 `our_engine_alive()`：以「跟踪的子进程句柄是否存活」作为「这个引擎是不是我们拉起来的」唯一判据。
- 新增 `kill_port_owner(port)`：用 `netstat -ano -p TCP` 找 LISTENING 该端口的 PID → `taskkill /F /PID`；
  非 Windows 用 `lsof -ti` 兜底 `pkill -f "ollama serve"`。
  **按端口而非进程名杀**，所以绝不会误杀用户自装的、跑在 11434 的 Ollama（替换掉原来 `taskkill /F /IM ollama.exe`）。
- 新增 `ensure_our_engine(binary, model_dir)`：① 我方子进程存活 → 只等端口；② 端口被非我方进程占用
  → `kill_port_owner` 接管后重启（自带 `OLLAMA_MODELS`）；③ 端口空闲 → 直接拉起。
  `start_ollama_engine` 与 `ensure_local_provider` 都改走它。
- `local_model_exists()` 重构为 `find_local_model() -> Option<String>`（返回**仓库里的真实名字**）。
- `download_model` 返回值由 `()` 改为 `Result<String, String>`（真实模型名）；收尾前必须 `find_local_model` 命中，
  否则报错 —— 宁可报错也不给前端一个假的「已安装」。
- `cleanup_local_models(Some(name))` 先 `find_local_model` 解析真实名再删；找不到则明确报「未找到，无需卸载」。
- `LocalProviderStatus` 增加 `model_dir` 字段，把引擎实际模型目录透出给 UI。

**前端**
- `useOllamaEngine.ts` 新增导出 `normalizeModelId()` / `isSameModel()`（缺 tag 一律补 `:latest`）。
- `installedModelNames` 改为**规范化集合**；新增 `findInstalledName()` 查真实名。
- `syncProvider()` 用 `isSameModel` 找预设、用真实名做 `modelId`、默认模型也用规范化比较保留。
- `installModel()` 接收 Rust 返回的真实名 → `refreshModels()` → **校验确实在仓库里**，否则抛
  `local.errors.modelNotFoundAfterInstall`（干掉「假成功」这一类问题）。
- `uninstallModel()` / `setDefaultModel()` 都改用 `findInstalledName()` 得到的真实名。
- `startEngine()` 改为在 `start_ollama_engine` 之后调 `ensure_local_provider` 取回模型列表 + `model_dir`。
- `ollama.vue` 模板：`installed` / `isDefault` 全部走规范化比较；引擎操作区新增「模型目录」按钮（点击复制）+ 说明文案。
- i18n 5 语言新增 `labels.modelDir`、`local.hints.modelDirHint`、`local.errors.modelNotFoundAfterInstall`。

### 排查这类问题的有效手法（可复用）
```bash

# 2) 谁占着端口

# 3) 两个模型仓库分别有什么（对比就能看出引擎用的是哪个目录）

ls -la --time-style=full-iso <models>/blobs   # 时间戳能直接还原"哪次下载落在哪个目录"
```

## 本地大模型：apiKey 鉴权网关（防止局域网/同机其它用户白嫖）

### 关键事实（决定了实现方式）
- **Ollama 的本地服务没有任何鉴权**。官方文档明说本地 API 不需要认证；`OLLAMA_API_KEY`
  只对 ollama.com 云端生效，`ollama serve` **根本不读**这个变量。
- 官方给的加固建议只有两条：**让端口不可达** + **在前面放一个做校验的反向代理**。
- 因此"给本地模型加 apiKey 校验"只能自己做一层网关，否则就是安全剧场。

### 端口约定（**重要，后续改动请遵守**）
| 端口 | 归属 | 是否校验 | 说明 |
| --- | --- | --- | --- |
| 11434 | 用户自装的 Ollama | — | 我们绝不碰 |
| **11435** | **本应用鉴权网关** | ✅ apiKey | 客户端（含本应用）打这里；provider `baseUrl` = `http://127.0.0.1:11435/v1/chat/completions`（**完整端点**，见文末 404 那节） |
| **11436** | **Ollama 引擎（私有）** | ❌ | 仅回环，只给网关当上游；`build_ollama_client()` 指向它 |

Rust 常量：`ollama_manager::ENGINE_PORT = 11436` / `GATEWAY_PORT = 11435`（`pub(crate)`）。

### 落地改动
**新增 `src-tauri/src/ollama/gateway.rs`**
- `spawn_gateway(&AppHandle)`：`lib.rs` setup 里调用。先 `load_or_create_api_key`（同步，保证 webview 起来前就绪），
  再起线程 bind `127.0.0.1:11435`；bind 失败 → `kill_port_owner(11435)` 回收（旧版本 Ollama 曾占用此端口）后重试。
- 每连接一线程 `handle_conn(client, upstream_port)`：读请求头 → 校验 → 连上游 → 转发头 → 按 Content-Length 转发 body → 反向逐块管道并 flush。
- **鉴权**：`Authorization: Bearer <key>` 或 `x-api-key: <key>`，用 `constant_time_eq` 定长比较。
  失败 → 401 且**完全不接触上游**，body 是 OpenAI 风格的 `{"error":{"code":"invalid_api_key"}}`。
- **安全细节**：`should_strip_header` 剔除逐跳头 + `authorization` + `x-api-key`（凭据绝不流到上游）；
  `Host` 改写为上游；端到端 `Connection: close`（这样无需实现 chunked 分帧，SSE 仍逐块实时透传）；
  chunked 请求体明确回 411；body 上限 64MB（视觉请求带 base64 图）。
- **apiKey**：`rand::thread_rng()`（CSPRNG，`rand = "0.8"` 是本期唯一新依赖）+ `sk-pingyou-local-<40>`，
  落盘 `<app_data_dir>/local-gateway.json`；运行期由 `Mutex<String>` 持有，重置后**立即生效**无需重启。
  命令：`get_local_api_key` / `regenerate_local_api_key`。
- `is_gateway_ready()`：bind 成功后置位；写进 `LocalProviderStatus.gateway_ready`，
  避免"引擎健康但网关没起来"这种**静默失败**（UI 会直接报错而不是等用户发起对话才撞墙）。

**选型说明**：沿用项目既有范式（`utils/local_http.rs`）——`std::net` 手写 HTTP/1.1、不引框架。
没用 axum/hyper 是因为 lock 里虽然有 hyper，但手写管道 + `Connection: close` 已足够且零新依赖。

**前端**
- `useOllamaEngine.ts`：`apiKey` 状态 + `loadApiKey()`（幂等）/`regenerateApiKey()`；
  `ensureEngine`/`startEngine` 都**先 await loadApiKey 再 syncProvider**（顺序错了供应商 key 会为空）；
  `syncProvider()` 写入 `apiKey`，并用 `apiKey.value || existing?.apiKey || ""` 兜底防止误清空；
  启动检测里判断 `gateway_ready`。
- `ollama.vue`：引擎就绪区新增 apiKey 展示 + 复制 + 重置（Popconfirm，文案提示旧 key 立即失效）。
- i18n 5 语言新增 `labels.localApiKey/regenerateKey`、`local.hints.localApiKeyHint`、
  `local.errors.gatewayUnavailable`、`dialogs.regenerateKeyTitle/Content`、`messages.keyRegenerated/keyRegenerateFailed`。
- provider 的 `apiKey` 本身由 `provider-repository.ts` 用 `encrypt_string` **AES 加密后入库**，key 不会明文落盘。

### 测试（真实 TCP，不是 mock 逻辑）
`src-tauri/src/ollama/gateway.rs` 底部 `#[cfg(test)] mod tests`，跑 `cargo test --lib gateway`：
1. 无凭据 → 401，且上游**未被访问**（用 channel + `recv_timeout` 断言）；
2. 错 key → 401，上游未被访问；
3. 正确 key → 200 透传、SSE body 逐字节一致、请求体完整送达、`Authorization` 未出现在上游请求里、`Host` 已改写；
4. `x-api-key` 方式同样被接受且同样不外泄。
> 注意：全局 key 是进程级共享状态，所以**断言都放在同一个 `#[test]` 里串行执行**（另加一个用同一 key 的独立用例）。

## 本地大模型：聊天报 `404 page not found` + `payload.model` 类型报错

### 根因 1（404 的真凶）：`provider.baseUrl` 必须是**完整端点**
- 项目约定（`constants/provider.ts` 全部条目、`cloud-tab.vue` 里七牛 `https://api.qnaigc.com/v1/chat/completions`）：
  `provider.baseUrl` = **可直接 POST 的完整地址**。`useTauriAIChat.resolveEndpoint()` 在无 path 参数时
  把它**原样**当请求 URL 发出去（不补 `/chat/completions`）。
- 而本地模型当时写的是 `http://127.0.0.1:11435/v1` → 请求打到 Ollama 不存在的路由 `/v1`
  → 返回它默认的**纯文本** `404 page not found`。
- 辨伪要点：**网关只会产出 JSON 错误**（401/411/413/502），纯文本 404 一定来自 Ollama 本身。
  即"能收到 404"说明 apiKey 校验已通过、网关与引擎都是通的，只是路径错了。
- 修复：`OLLAMA_GATEWAY = "http://127.0.0.1:11435"` → `OLLAMA_BASE_URL = \`${OLLAMA_GATEWAY}/v1/chat/completions\``，
  `OLLAMA_HOST` 与之取同一个值（UI 展示/复制的地址）。

### 根因 2：`DownloadPayload` TS 接口漏了 `model`
- Rust 侧 `DownloadPayload` 早已有 `model: String`（进度按模型路由），但 TS 侧
  `stores/shard/app-shard.ts` 的同名接口没跟上 → `payload.model` 报"类型上不存在属性 model"。
  补 `model?: string` 即解决。

### 顺手修掉：退出后残留的孤儿 `ollama.exe`（这正是"端口被劫持"的源头）
- 实测：应用已完全退出，`ollama.exe` 仍 LISTENING 在 11436（进程启动时间 = 上次应用运行时间）。
- 修复：新增 `ollama_manager::shutdown_engine_blocking()`（同步 kill 自己拉起的子进程），
  在 `lib.rs` 的 `app.run(...)` 里挂到 `tauri::RunEvent::Exit` 分支 —— 退出时刻不能再 spawn 异步任务，所以必须同步实现。

### 端到端诊断手法（应用没开也能用，实测有效）
```powershell
# 直接对端口发请求，就能分辨 404 来自哪里（无需 apiKey）
POST http://127.0.0.1:11436/v1                  -> 404   （Ollama 路由不存在：证明 404 是 Ollama 产的）
POST http://127.0.0.1:11436/v1/chat/completions -> 200   （上游本身正常）
# 端口判读：11435 连接被拒 = 网关没起来（应用没运行 / bind 失败）；有响应但 401 = 网关正常、key 不对
```
流式响应格式已实测与前端解析器完全对齐：
`Content-Type: text/event-stream`，每行 `data: {"choices":[{"delta":{"content":"..."}}]}`，以 `data: [DONE]` 收尾。

## 聊天窗口优化：思考中状态 / 视觉图片上传 / pingyou 卡片聊天入口 / 气泡窗美化

### 根因 bug：`useTauriAIChat()` 每次调用都新建 ref（「思考中」永远不显示）
- 原实现把 `loading` / `error` / `hisMessages` / `abortController` 定义在 `useTauriAIChat()` **函数体内**，
  但多处是 `computed(() => useTauriAIChat().loading.value)` 这种写法 → **每次求值都是一组全新的 ref**，
  永远是初始值（false / 空） → `chat-area.vue` 的「思考中 / 停止」按钮永远不出现。
- 修复：把这 4 个状态提到**模块级**共享单例（函数外 `const loading = ref(false)`），
  `useTauriAIChat()` 只返回同一组引用。凡是「composable 里放状态 + 用 computed 反复调用它」的组合，
  状态必须模块级，否则必出这类幽灵 bug。

### 多模态（视觉模型）
- `TauriAIChatRequestOptions` 新增 `file?: TauriAIChatFileOptions` 与 `allowVision?: boolean`
  （**显式开关**：非视觉模型即使带了 file 也绝不拼进请求）。
- `buildUserContent(text, file, isAnthropic, allowVision)`：OpenAI 走
  `[{type:'text'},{type:'image_url',image_url:{url:dataUrl}}]`；Anthropic 走
  `[{type:'image',source:{type:'base64',media_type,data}},{type:'text'}]`。
- 视觉判定：`isVisionModel = target?.type === 'vision'`（`provider-shard.ts` 的 `ModelCapability`）。
  非视觉模型带图 → 抛 `composables.useTauriAIChat.errors.modelNotVision`。
- 新增 `src/utils/chat-image.ts`：`readImageFile()` 校验类型 + 大小（`CHAT_IMAGE_MAX_BYTES` = 8MB）→
  `{ name, mediaType, dataUrl, base64 }`；`pickFirstImage()` 取粘贴/拖拽的第一个图片。
- UI：chat-area / winchat 都有图片按钮（`canSendImage` 为真才显示）、图片预览条、`handlePaste` 支持截图直贴。

### 气泡窗（winmsg）状态机：与答案文本**双通道**解耦
- 新增 `LISTEN_KEY.CHAT_BUBBLE` 事件 + `CHAT_BUBBLE_STATE`（thinking/streaming/done/error）。
- 为什么单开通道：原来只有 `WINDOW_MESSAGE` 一个通道，`THINKING` 哨兵值会被随后流入的答案文本**冲掉**。
- `winchat/index.vue` 提交时先发 THINKING 状态，再走 STREAMING/DONE/ERROR；
  事件体带 `conversationId`，`winmsg` 据此判断是否属于当前会话。
- `winmsg/msg.vue` 卡片化气泡：头部（头像+标题+状态+复制/关闭）、尾巴（左右/跟随 `WINDOW_POSITION`）、
  正文（思考中/错误/流式 markdown/空闲四态）。
  - 自动适配窗口高度：`fitWindow()` 宽 360、高 clamp 108–460，带 **8px 抖动抑制** + `fitting` 重入锁。
  - 该文件样式是**非 scoped**，所以按钮用原生 `<button class="bubble-icon-button">`，
    不用 antd `Button`（避免类名前缀在跨窗口下丢失）。
- 暗色主题：`winmsg/winchat` 是独立 webview，`App.vue` 里加了
  `watch(() => generalStore.appearance.isDark, v => document.documentElement.classList.toggle('dark', !!v), { immediate: true })`
  把暗色同步到每个 webview（否则气泡窗永远是亮色）。
